Simulation · Cumminsville Comfort

Swap the LLM for a decision model

Cumminsville Comfort is a made-up heating shop in Cumminsville, Cincinnati. Web forms, texts, and emails have to be routed. A large model can label each one. A small decision model can return a probability per label and a confidence, and skip the paragraph.

Andrew bookmarked @badlogicgames (Mario Zechner):

classifiers are all you need. bonus points if you use an llm to generate labeled data to train idiot models and then replace the llm with it

That post links Amazon saves millions replacing Sonnet with Strands Decider (Nov 9, 2026). This page simulates the pattern on 36 fictional messages. It is not Amazon’s classifier and not a trained model.

Simulation, not a trained model. Cumminsville Comfort, the messages, and the probabilities are fictional and scripted in this tab. The decision model matches the LLM on clear messages and is weaker on ambiguous ones. A key-order nudge is capped at the 0.19 the post reported. Nothing is uploaded. The page does not call a network or a model.

Numbers the post reported

Amazon’s task was 20 categories plus a “none” option. This shop has 7 labels. The prices below are the post’s figures, not a measurement from this page.

  • Claude Sonnet 4.6. 4,215 ms average. 6,554 input tokens and 170 output tokens. About $0.0222 per ticket, about $22,200 per million tickets. Token prices they used: $3 per million input, $15 per million output. That token math is $0.022212, which they round to about $0.0222.
  • Strands Decider E4B on SageMaker ml.g5.xlarge at $1.408 per instance-hour. 897 ms per call. 2,009 input tokens and 1 output token. At about 640 ms per request, about 5,600 tickets an hour on one instance. About $250 per million tickets at full use, about $500 per million with headroom. About 44× cheaper, a 98% reduction.
  • The switch was a value read from AppConfig on every message: BEDROCK (LLM only), DUAL (both run, LLM result applied, disagreements compared), or DECIDER (decision model only). Rolling back was a 45-second config change.
  • Key order. JSON key order changed output probabilities by up to 0.19, so they sort keys on every request. They tuned a confidence threshold before applying a label. Each label’s long description was rewritten as a 1–2 sentence criterion.

The catalog, as short criteria

A closed list. The post’s point is that this shape of task can leave the LLM.

  • Emergency, no heat. The heat is off, the home is cold, or someone reports a gas smell. They need a person today.
  • Maintenance booking. They want a tune-up, a filter, or a seasonal visit, and the system is still running.
  • Quote request. They want a price for equipment or a replacement before anyone is booked.
  • Billing question. They are asking about a charge, a refund, an invoice copy, or how to pay.
  • Warranty claim. Something this shop installed or replaced has failed, and they want that coverage honored.
  • Spam or vendor pitch. A seller, a lead broker, or an agency wants the shop's money or its customer list.
  • Other / none. None of the labels fit. Hours, a thank-you, a wrong number, or a job note with no emergency.

Confidence threshold

    
Below the cutoff the decider abstains. Send those to a person, or fall back to the LLM. Accuracy is the share it gets right on the messages it still labels. Coverage is how many it labels. Fallback rate is the rest.

Cost and latency

    
Per-ticket figures from the post. The decider still runs on every message, so its price does not fall when it abstains. What changes is how often you also pay for a person or for Sonnet.

    
    
    
2,0001M+

    

    

    

    

    

    
At small-business volumes the dollar savings are tiny. The real wins are latency, privacy (the model runs locally, self-hosted), and predictability. At high volume, the savings dominate. The post’s per-ticket rates assume the instance is busy. A box left on all month costs about the same whether you send 2,000 messages or none.

  


  

    
Key order

    
The post says JSON key order changed output probabilities by up to 0.19, so they sort keys on every request. This simulation applies a fixed nudge, never larger than 0.19. It is not their model. Shuffle the keys, watch a borderline label flip, then sort them.

Use an LLM to label, then train a small one

    
    
      
  1. Write each label as a one- or two-sentence criterion. The post says they rewrote the long descriptions this way.
    2. 
      
  2. Use an LLM to label a large set of real messages with those criteria.
    3. 
      
  3. Train a small decision model on that set. It returns a probability per option and a confidence, not a paragraph.
    4. 
      
  4. Run both on every message, keep the LLM label, and read the disagreements. Pick a confidence threshold. Then flip the config to the small model. The LLM path stays one config change away.
