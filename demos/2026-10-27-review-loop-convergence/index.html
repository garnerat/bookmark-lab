Make the review loop finish

Madisonville Comfort is a made-up heating shop in Cincinnati. This pull request adds after-hours booking. An agent wrote the patch. Another agent reviews it, the author answers every comment, and the review runs again.

The setup is from How the Claude Code team does code review by Addy Osmani, Morgan Westlee Lunt, and Qing Wang. The same essay is on the claude.dev blog. From June to September, merged pull requests to Claude Code more than doubled, and the share that had to be reverted fell by more than 40%.

These numbers are a toy. The coin flips were picked so the failure is easy to see on a phone. They are not measurements of Claude, GitHub, or that team. The 50-round pull request, the figure of about 59%, and the double-the-merges result are from the article. Nothing on this page reproduces those measurements.

The article describes six layers of checks, most of them automatic, with a fast rollback under them. A person’s attention goes to the risky part.

  1. Verify the work before a pull request exists. Tests, a build, a screenshot, a fresh-context pass.
  2. AI review on the pull request. Several agents look for bugs. A finding is posted only if enough voters agree it is real. This page is about that loop.
  3. A security review that can block the merge.
  4. CI that can block: lint, types, tests, build.
  5. A person approves. Riskier changes need more people. The risk comes from the change, not from who typed it.
  6. A merge queue, feature flags, and a staged rollout. Employees see it before the stable channel does.

Some bugs still get through. Flags and a one-step revert are the last layer.

Inside the AI review, the author and the reviewer have to stop. One pull request in the CLI repo went through more than fifty rounds overnight. The author stopped it by hand. It could have kept going. A blame check on what the reviewer kept flagging found that about 59% was code already present on the first pass. The reviewer was mostly finding a few more old notes each round, not new bugs from the latest edit.

Their change: cap the full passes at three, then re-review only the new diff. Also name the class of bug so the author fixes every instance, and do not post a finding that was already posted. This toy has switches for the cap, the diff-only follow-up, and the vote. It does not simulate the class-of-bug rule or the “already posted” memory beyond a simple repeat.
