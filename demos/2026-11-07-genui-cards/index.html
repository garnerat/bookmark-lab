Fictional sample · Copper Lantern Roofing

A chat card instead of a wall of text

Copper Lantern Roofing is a made-up shop in Hyde Park, Cincinnati. The owner asks its agent what is on tomorrow, which of two roof quotes to send, or how leads looked this week. A plain reply is one long paragraph. With a typed catalog, the model writes a JSON spec instead, and json-render turns that spec into a chat card.

The idea is from Guillermo Rauch’s post and the November 6, 2026 Vercel changelog, Chat SDK agents can stream generative UI with json-render. One spec posts as Slack Block Kit, a Teams Adaptive Card, or a web card. The docs are @json-render/chat, and the code is in vercel-labs/json-render.

Copper Lantern Roofing is fictional. Hyde Park, Mt. Lookout, Madisonville, and East Walnut Hills are neighborhood labels. Crews are labels, not people. Every dollar, lead, and job time is example data. Nothing is uploaded. This page does not call a model, a network, or an API.

One spec, three native cards

The agent is not allowed to invent a layout. It can only emit components from a catalog. json-render checks that JSON and hands a card to the chat adapter. Slack, Teams, and the web each draw the same card in their own format.

  1. Catalog. The allowed components are Card, Section, Text, Fields, Field, Table, Chart, Divider, Image, Actions, Button, and LinkButton.
  2. streamCard. The card is posted once the root Card exists. Later elements edit that same message, at most once every 500ms.
  3. toCard. Every element’s props are checked against its schema. A bad spec throws CardSpecError. Each problem is one readable issue the model can fix.
  4. limits. Slack turns a second table into a code block. Pass limits and toCard rejects the spec instead of letting the adapter degrade it.

The catalog is the guardrail

    
These are the standard chat components. If it is not on this list, the agent cannot emit it, and toCard reports an unknown component.

    
    
      
  • Card Root of the message. It needs a title, an image, or a child.
    • 
      
  • Section Groups related elements inside the card.
    • 
      
  • Text A markdown paragraph. Styles are plain, bold, and muted.
    • 
      
  • Fields A grid of label and value pairs. Children are Field elements.
    • 
      
  • Field One label and one value, inside Fields.
    • 
      
  • Table Headers and rows. Slack turns a second table into a code block.
    • 
      
  • Chart A pie, bar, line, or area chart.
    • 
      
  • Divider A line between groups.
    • 
      
  • Image An image from an https URL, plus alt text.
    • 
      
  • Actions A row of Button and LinkButton elements.
    • 
      
  • Button An action the bot handles. It needs an id and a label.
    • 
      
  • LinkButton A button that opens a URL.
    • 
    

    
Not in the standard chat catalog, even if a model reaches for them:

    
    
      
  • Callout Not allowed. A bad spec that emits it gets an issue back.
    • 
      
  • Metric Not allowed. Use Field inside Fields.
    • 
      
  • Stack Not allowed. Use Section.

Why this matters

    
A shop owner asking about tomorrow does not need a paragraph to scan. The same three stops, the same 6.5 hours, and the same first arrival fit in fields, a chart, and a table, with a button for the next step. The catalog is what keeps that card from becoming whatever markup the model felt like writing.

    
The stream is the other half. The message goes up when the root Card exists, then fills in about every 500ms, instead of waiting for a finished essay. If the model emits a radar chart, a Callout, or a second table past the cap, toCard does not guess. It returns the issues, and the model tries again.
