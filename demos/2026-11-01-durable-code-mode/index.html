Code mode that survives a crash

Linwood Comfort is a made-up heating-and-cooling shop on the east side of Cincinnati. Its agent has to answer one question from the job board. Direct tool calls hand every payload to the model. Code mode keeps that data inside a script. If the script dies halfway, a journal decides what runs again.

The idea is from Code mode that survives a crash by Manoj (@manojlds). The full post is Code Mode That Survives a Crash. @badlogicgames shared it here.

Linwood Comfort is fictional. The jobs, crews, and parts prices are a sample. Crew names are dispatcher codes, not people. Nothing is uploaded. The page does not call a model or a network.

Forty-eight fake jobs are on the board. The matching ones are completed, tagged warranty, and closed in October 2026.

Three ways a tool result can come back

  1. Direct calls. The model asks for one call. The harness runs it. The full result is written into the model’s context before the next turn. List, then detail, is a chain: each link is another turn, and the raw JSON stays in the conversation.
  2. Code mode. The model writes one script. The script calls list_jobs and get_job as functions in a sandbox. Pages and job details stay in the script. The model sees what the script returns.
  3. Durable replay. A crash throws away the JavaScript stack. The script runs again from the top. Each tool result was saved in a journal before the script saw it, so a finished call returns the saved result instead of running again.

The sandbox is deterministic: a virtual clock, random numbers from a fixed seed, and UTC. A tool marked safe may run again if the crash cut it off mid-flight. The default is unsafe: that in-flight call becomes an error, because it may have partly run. Resume also errors if the script asks for a different call than the journal, if the sandbox changed, or if the time limit ran out. It does not notice when the data behind a finished call has changed.

Running model-written code has its own costs: a sandbox, a person approving a call in the middle of a script, work that fails halfway, and a restart that has to decide what already ran.

The question

Total callbacks and parts cost per technician for completed jobs tagged warranty last month.

Last month in this sample is October 2026. The board calls technicians by crew code: Oak, Maple, Birch, and Cedar. The tools are list_jobs(page) and get_job(id). A page holds 12 jobs and does not include callbacks, parts, or notes. Those are on the detail.

The author’s small Pi experiment

Those counters are not the figures below. Manoj ran one task a handful of times in the Pi coding agent and said it is not a benchmark. Tool output reaching the model dropped from 26,820 bytes to 4,374. The cost Pi logged dropped from $0.037 to $0.021. OpenCode on the same task still returned the full list to the model. With only two tools, the code-mode tool also made the first prompt larger. This page does not reproduce that run.

Crash the script, then resume

The journal lists every call. A result is saved before the script sees it. Crash now kills the script while a call is in flight. Resume reruns the script from the start against that journal.

A side effect stays unsafe

book_followup_visit books a warranty review. It is separate from the crash above. The call is in flight, the server may already have booked the visit, and the script never saw the result.

Leave the tool unsafe so a crash does not fire it again. Still send an idempotency key. The interrupted call may have landed, and a later retry has to find that visit instead of booking a second one. Marking it safe replays the call automatically, which is the wrong place for a side effect.

When to use it

In the script: bounded reads, and the filtering and counting that follow. A safe replay policy fits those reads. A crash costs at most one repeated lookup.

Outside the script: long waits, approvals, and side effects. The model should see those results before it takes another step. A side effect stays unsafe, and it carries an idempotency key.
