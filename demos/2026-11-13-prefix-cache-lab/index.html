Prefix Cache Lab: why long local chats feel slow

Brindle & Quill is a made-up two-lawyer firm. Client drafts stay in the office, so a paralegal asks a private model on a Mac mini about intake and about one pasted contract. The long shared prefix is the firm instructions, an engagement-letter template, and that contract. Each follow-up question is short. The wait before the first word is the engine reading tokens, not the Mac struggling to think.

Andrew bookmarked @CerebralCoding_, 12 Nov 2026:

Your Mac was never slow at long chats. Your engine kept re-reading them. Qwen 3.8 27B on a 64GB M5 Pro Mac mini, TensorFold: 1.2.6: a follow-up re-reads 24K tokens, 76.8s before the first word. 1.2.7: reuses ~34K cached tokens, first word in 0.34 to 1.19s. Same box. Same model.

The slider defaults to 315, so 24,000 tokens take 76.2s in this simulation. That is a round neighbor of 76.8s, not a fit to TensorFold.

Same contract, two engines

No cache prefills the whole history on every turn. Prefix cache prefills the history once, then only the new question, if the opening tokens still match. The first turn is cold either way: nothing has been computed yet. The gap is the follow-ups.

    Why a matching prefix can be kept

    The model builds a key and a value for each token it has already read. That pair is the KV cache. The next token attends to those pairs. If the conversation still begins with the same tokens, the pairs from last time are still right, and the engine can skip them. It prefills only the suffix that differs. Time to the first word then follows the new tokens, not the whole history.

    Attention looks backward. The key at a position was computed from everything before it. Change a token, and every key after that position is stale. Tokens before the change never looked at it, so they can stay. A timestamp in the first line throws away the contract. An edit to the first question keeps the contract and recomputes the tail. Putting the clock at the end of the prompt, after the stable text, leaves the long prefix reusable.

    The first request still pays the full prefill. The cache is empty until something has been computed. A later request also misses if it lands in a different slot that does not hold this prefix.

    The cache costs memory

    Keeping the prefix means keeping those keys and values. The cache grows in a straight line with context. This bar is approximate. It is not a measurement of Qwen 3.8 27B, TensorFold, or a 64GB Mac mini.

    The sketch charges 262,144 bytes of KV state per token: 2 × 64 layers × 8 KV heads × a head size of 128 × 2 bytes. That is fp16 cache for a made-up 30B-class model with grouped-query attention. A real model may use another shape. A runtime may store KV in q8 or q4, which is smaller. Model weights are not in the bar. The track is 64 GB only because the post’s computer had 64GB of unified memory. Each extra 10,000 tokens adds about 2.44 GB on this sketch.

    Try it yourself

    On your own machine, a local server can reuse a prefix when the next prompt starts with the same bytes. This page does not run that server. Flag names move. The notes below match the llama.cpp server README as of this writing. Check the README for the version you run before you rely on a default.

    llama-server documents prompt caching on POST /completion. cache_prompt defaults to true. The server compares the prompt with the previous completion in that slot and evaluates the suffix that differs. --cache-prompt is on by default. --no-cache-prompt turns it off. id_slot pins the chat to one slot. The default id_slot is -1, which assigns an idle slot, and an empty slot prefills from scratch. The README also says logits are not guaranteed to be bit-for-bit identical when the batch size changes, so a cache hit can be nondeterministic.

    curl --request POST \
  --url http://127.0.0.1:9931/completion \
  --header "Content-Type: application/json" \
  --data '{
    "prompt": "<same instructions, letter, and contract as last time>\nParalegal: <only the new question>",
    "cache_prompt": true,
    "id_slot": 0,
    "n_predict": 128
  }'

    The port 9931 is the one in the current server README’s curl example. Yours is whatever you passed. Keep the prefix identical, including spaces. Put a timestamp after the contract, not in front of it.

    Ollama’s chat response can include prompt_eval_count and prompt_eval_cached_count. A cached count above zero means that runner reused prefix tokens. Some runners reuse a shared prefix and some re-evaluate it, depending on the model and the build. LM Studio has written up KV restore for a matching prefix in its MLX engine. Other MLX apps differ. This page does not name a checkbox in those apps. Check the runtime’s docs.
