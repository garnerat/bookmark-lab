Will this MoE fit my Mac?

Ledger & Lane Accounting is a fictional 6-person accounting practice that wants a private local model on one office Mac so client tax documents never leave the building. The number on the model card is the wrong one to shop with.

Andrew bookmarked @CerebralCoding_, 16 Nov 2026, quoting @superalesha:

Your 128GB Mac was never too small for a frontier MoE. The MoEs were too fat. Hy4 flash vs DeepSeek V4.1 Flash, sized for home: Hy4 flash: 224B total, 12B active, about 80GB of real weights at 4-bit. DeepSeek V4.1 Flash: about 290GB of FP4 experts alone. 64B of Hy4 flash is an Engram lookup table, read a few rows per token, so it can sit on the SSD. The rest fits in a 128GB Mac. Tencent puts it level with or above DeepSeek V4.1 Flash on agent tasks. Weights aren't public yet. That's the only thing missing.

A planner, not a benchmark, and not a copy of either model. The sizes above are the posts’ figures. Every fit label and every tokens/sec number on this page is a rough back-of-envelope estimate, not a benchmark. The model figures come from the linked posts. Gigabytes here are decimal, 1,000,000,000 bytes, so (224 − 64) × 4 / 8 is 80 GB rather than about 74.5 GiB. Nothing on this page loads a weight, calls a runtime, or leaves the browser. The posts' arithmetic

(224B − 64B) × 4 bits / 8 = 80 GB. That is Hy4 flash once the 64B Engram lookup sits on the SSD. The headline 224B × 4 bits / 8 = 112 GB is the wrong number to size a Mac by. Speed follows the 12B that are active: 12B × 4 bits / 8 = 6 GB moved per token.

  • Hy4 flash, from both posts: 224B total, 12B active, 1M context. 64B of the 224B is Engram, DeepSeek’s lookup-table memory, read a few rows per token. The quoted post’s 4-bit line is about 80 GB of real weights, and a 128 GB Mac holds those weights in unified memory. It also lists about 3.2 bits per weight, about 64 GB, for a three-GPU pile. This page’s 3-bit button is 3.0, not 3.2, so it will not match that 64 GB line. 160 × 3.2 / 8 = 64, and 160 × 3 / 8 = 60.
  • DeepSeek V4.1 Flash: about 290 GB of FP4 experts alone, and the quoted post says that is before Engram. 290 × 8 / 4 = 580B is this page’s conversion so the same formula can run. It is not a parameter count the posts published. They also do not publish how many parameters are active.
  • KV cache is a slider, not a model card. The quoted post says hybrid attention plus LatentMoE cuts KV cache to 1/6 of Hy4 and 1/24 of Hy3, so 1M context will not eat VRAM. It does not say bytes per token. The default here is a short office working set, 32,768 tokens, not the 1M maximum.
  • A related bookmark from @ivanfioravanti is the other switch: run DeepSeek V4.1 Flash on a 32–64 GB Mac by streaming experts from the SSD. This page does not have a status link for that post. The streaming toggle is that idea, drawn as a sketch.

    Which Mac for the practice

    Ledger & Lane Accounting is a fictional 6-person accounting practice that wants a private local model on one office Mac so client tax documents never leave the building. One computer in the office. No return is uploaded anywhere.

    The quoted post says the 4-bit Hy4 flash weights fit in 96 GB of VRAM, with room for context, and that a 128 GB Mac holds them in unified memory. VRAM in that line is not also running the office. With 20–25% held back, the same 80 GB does not fit a 96 GB Mac.

    tokens/sec ≈ bandwidth ÷ (active params × bits / 8). Engram is not in that divisor. The posts say it is a few rows per token, not a scan of the whole lookup table. Streaming replaces memory bandwidth with the SSD stand-in for the whole active read. That is the harsh end. A runtime that keeps hot experts in RAM will beat it.

    The gotcha

      Try it yourself

      On a machine you control, a quantized local runtime is how you would check a real file. This page does not run either command. Hy4 flash weights are not public yet. The bookmarked post says that is the only missing piece, so there is no Hy4 file to point these at today. Flag names move. Read the README for the version you install. Q4_K_M is a 4-bit-class GGUF quant, not exactly 4.0 bits on every tensor. The 4-bit button above is the plain bits/8 sketch.

      # Sketch of a local run. Not a benchmark, and not a download.
# Hy4 flash weights are not public yet.

# llama.cpp, after you have a GGUF you are allowed to use.
# -ngl 99 asks for as many layers as the GPU path will take.
llama-cli -m ./model-Q4_K_M.gguf -c 32768 -ngl 99

# MLX on Apple Silicon, after a 4-bit conversion.
mlx_lm.generate --model ./model-4bit --max-tokens 128

      llama.cpp’s quantize tool builds a GGUF such as Q4_K_M. MLX’s convert path has a 4-bit quantize option. Streaming cold experts from an SSD is a separate runtime feature. This page does not invent a flag for it. Check the docs before you rely on a default. Keep the practice’s documents on that Mac.
